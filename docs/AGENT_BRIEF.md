# Brief for game-hook agents (PlayJev)

You are turning one or two vendored browser games into deterministic, steppable environments.
Repo root: this checkout. Python venv: `source .venv/bin/activate`
(Playwright 1.63, chromium headless shell installed). Node is available for syntax checks
(`node -e "new Function(require('fs').readFileSync('games/<id>/pj_hook.js','utf8'))"`).

Read first, in this order:
1. `docs/HARNESS.md` (the contract; everything you write must satisfy it)
2. `games/_shared/pj_shim.js` (what `pj` provides; do NOT edit this file, report bugs instead)
3. `games/snake/pj_hook.js` and `games/snake/pj.json` (reference implementation)
4. `playjev/env.py` and `playjev/bench.py` (the driver; do NOT edit them)

Then, for each of your games:
1. Read the game's source enough to know: how the loop is driven, where state lives (globals,
   closures, class instances), which keys it listens for and on which element, how a game
   starts, how it ends, what a natural score is.
2. Write `games/<id>/pj_hook.js` and `games/<id>/pj.json`. Prefer leaving the vendored code
   untouched. If you must patch it (for example to expose an instance that is only a local
   variable), keep the patch minimal, and record the exact change in `games/<id>/NOTES.md`.
   Never rewrite game logic, never change rendering.
3. Run `python -m playjev.bench <id> --pages 8 --steps 200` until it is clean: no `errors`
   lines, the game visibly advances across the saved frames in `runs/bench/<id>/`, the score
   moves, episodes end when they should. Look at the frames with the Read tool (they are JPEGs).
4. Determinism check: two pages, same seed, same action sequence, same scores and same `info()`
   at every step. Put the check in `games/<id>/check_det.py` (copy the pattern from the bench).
5. Write `games/<id>/NOTES.md` (loop mechanism, state globals, what one step means in game
   time, action set rationale, quirks, throughput number from the bench).

Rules:
- Frames must be the play area only (canvas path preferred, about 2 ms; DOM games paint into an
  offscreen canvas the way Snake does). No page chrome, no menus, no help text in the frame.
- Actions are what a player would do; include `noop` only when doing nothing is a real choice.
  Descriptions are one plain sentence each, no game name in them.
- Score is monotone non-decreasing within an episode and never negative. If the game's own score
  is not a good learning signal (for example a racer), define one from progress and say so in NOTES.
- `done()` must be false right after `start()` and become true within the step that ends the game.
- One decision per step should be meaningful: for real-time games choose `stepFrames` so that a
  step is about 60 to 130 ms of game time (4 to 8 frames); for turn-based games one step is one move.
- Multi-level games: `start(seed)` may choose the level from the seed so episodes vary.
- Never kill processes by name or pattern on this shared machine; the driver starts its own
  server on a free port and closes it, and any background process you start yourself you stop
  by its recorded PID only. Do not touch anything outside `games/<your ids>/`.
- Scratch files: several agents run at once and share the session scratchpad; put your probes in a subfolder named
  after your game (for example `runs/probe/<id>/`), never at a shared top level.
- Time budget: 75 minutes wall clock per game. If a game resists after that, write down exactly
  what blocks it in NOTES.md and stop.

Final report (in your last message): per game, the action list, throughput (env-steps/s at 8 pages),
random-policy mean score and episode length, whether the determinism check passed, any vendor
patch, and anything the shim or driver should change.
